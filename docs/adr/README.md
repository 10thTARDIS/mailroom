# Architecture Decision Records

Every architectural decision is recorded here (spec §16). Seeded from spec
v0.4 Appendix A (decision log D1–D11), which was produced by the
pre-implementation design review. Deviating from the spec requires a new ADR
superseding the old one — see `CLAUDE.md`.

| [ADR-028](ADR-028-ingest-only-mode.md) | Ingest-only mode is a per-account `writeback_enabled` boolean (NOT a third `sync_scope` value — a move has two mailboxes); the real control is that no `IMAPWriter` is ever constructed; suppressed intents are a ledger that lifting the mode never drains; flags mirror the server while labels/filing/trash stay local; submission is disabled | Accepted |
| [ADR-029](ADR-029-mute-archives-in-mailroom-only.md) | Mute archives a new INBOX reply in Mailroom only (the skip-inbox placement, no writeback), leaves it unread and sends no push — a deliberate deviation from spec §6's "writeback where representable"; forward-only both ways; the opt-in thread merge can drop a mute | Accepted |
| [ADR-030](ADR-030-threading-is-reference-hint-matching.md) | Threading is Message-ID/References hint matching with the first match winning: no subject fallback, no cross-thread merge, a deliberate deviation from spec §4. | [ADR-031](ADR-031-area-labels-are-local-only.md) | Areas' own labels stay local-only (no keyword atom, nothing written to the mail server), a deliberate deviation from spec §6's sync-by-default; local labels are read through `Email.labelIds` and applied with `labelIds/<id>`, and re-file swaps area labels | Accepted |
| [ADR-032](ADR-032-learned-placement-from-the-users-own-filings.md) | Learned placement: a new message from a sender the user has filed at least twice, consistently, into one area is filed there at ingest (`applied_by = 'learned'`), with the From address as the key and the domain only as a fallback; learns only from the user's own filings; every placement is logged, a correction blocks the key, and each area stops acting when the 95% Wilson lower bound on its kept rate falls below 0.80 over 20+ outcomes; acts only on an authenticated sender (trusted DMARC pass when authserv-ids are configured) and never over a sender warning; no domain fallback for freemail or the user's own domains; per-user off switch, default on (amends ADR-023: its measurements came from a mailbox without history) | Accepted |
| [ADR-033](ADR-033-icalendar-is-a-small-in-house-parser.md) | Calendar invitations are read and answered by a small in-house RFC 5545 subset (`internal/ical`) rather than go-ical or golang-ical: every bound (bytes, components, properties, nesting, parameters, attendees) is enforced while parsing, recurrence is summarised and cannot be expanded, Outlook's Windows zone names resolve from the file's own VTIMEZONE, and the package imports no network code. Revisit when CalDAV (#15) needs a round-tripping object model | Accepted |
| [ADR-034](ADR-034-out-of-office-is-a-provider-sieve-script-outside-the-ledger.md) | Out of office is one Mailroom-owned ManageSieve script (`mailroom-vacation`). Turning it on is refused, and nothing is saved, while any other script is active. Turning it off restores the previous state (nothing active). Drift is shown and never repaired by force. The window is enforced by a `currentdate` guard and by start and end jobs. The replies are sent by the provider and are outside the outbound ledger, a stated deviation from spec §5 | Accepted |
| [ADR-035](ADR-035-date-bounded-authserv-trust.md) | `MAILROOM_AUTHSERV_IDS` entries may be `id<YYYY-MM-DD`: trusted only for mail whose `received_at` (a provider INTERNALDATE, never the Date header; archive-imported rows get the zero time) is strictly before that date, resolved per message by `ml.TrustedAt`, with an unresolved bounded entry matching nothing; a malformed bound is a startup error. The `authResults` notice is unchanged by untrusted headers and by the From address; it is null only for locally authored or Sent/Drafts mail. The "silence untrusted-only mail" half of an earlier decision was withdrawn (an attacker-writable header must not suppress a warning). Amends the earlier trusted-authserv rule | Accepted |
| [ADR-036](ADR-036-local-dkim-at-ingest.md) | Mailroom verifies DKIM itself at IMAP ingest, only for mail with no trusted Authentication-Results (an `x=` expiry makes later verification fail most mail): the verdict is stored in `app.message_local_auth` in the ingest transaction (no change row of its own), only an ALIGNED pass (PSL-based) is displayed as "Verified by Mailroom" and counts for selfSpoof, a local fail is never displayed, a provider verdict always wins; DNS bounded (3s a lookup, 4 lookups, 8s a message), a DNS failure stores nothing; a header-prepend/add guard requires every displayed identity header to be signed. No backfill | Accepted |
| [ADR-037](ADR-037-decrypt-on-open-plaintext-never-persisted.md) | PGP/MIME mail is decrypted on open by the crypto process (`decrypt`, go-crypto does all OpenPGP work) only when Email/get asks for body properties, and the plaintext is NEVER persisted: no column, blob, index, snippet, ML feature or cache — so the index never holds it and the LUKS-on-index gate does not land with decryption (deviates from spec §7; encrypted mail is not searchable). One opaque error, SED refused, 32 MiB output cap, per-user rate limit, an append-only audit row written by the crypto process, retired keys still decrypt; only MIME content fields cross from the decrypted entity; attachments scanned on demand at download; `SO_PEERCRED` declined again | Accepted |
| [ADR-038](ADR-038-encrypt-to-known-keys.md) | Outgoing mail is signed (`sign`) then encrypted by the crypto process's `encrypt` verb (go-crypto; SEIPD only; no private key used) to the recipients and to the sender's own key, so the Sent copy stays readable; rewritten at Submit like signing, drafts never encrypted, Bcc refused. Which key an address gets is a trust decision: only imported, WKD, or Autocrypt keys whose carrying message was authenticated for its From domain; the key must be usable and name the address; imported > WKD > authenticated Autocrypt; the fingerprint encrypted to is pinned (trust on first use) and a changed key refuses the send until confirmed | Accepted |
| [ADR-039](ADR-039-signature-display-and-key-changed-decision.md) | A PGP signature is one Email property, `pgpSignature`, with four honest states (verified / bad / unknownKey / keyChanged) for both signed mail and a signature inside decrypted mail. `verified` needs a key that names the From address AND an eligible source (the encrypt path's own rule), and an unauthenticated Autocrypt key never verifies. The first eligible verification pins the key; a different one is `keyChanged`. `ContactKey/decide` records trust (key becomes the pin and an imported key, so encryption uses it) or keep (key refused, never encrypted to), with a Contact change_log row; migration 00069 adds `contact_keys.refused` | Accepted |
| [ADR-040](ADR-040-key-lifecycle.md) | PGP key lifecycle. A re-sighted correspondent key (same fingerprint) is MERGED GnuPG-style, never replaced: union of user IDs, subkeys and verified self-signatures, forged signatures and third-party certifications dropped, so a renewal extends, a replay cannot shorten, a revocation survives; a real change writes the Contact row, a no-op none, the pin is untouched. New keys expire after two years (primary and encryption subkey; `--expires-days`, 0 = never). `pgp-retire` (store-only: decrypt-only, unpublished, refuses a bound default without `--unbind`) vs `pgp-revoke` (crypto process, real revocation signature, confirmed by fingerprint suffix); `pgp-extend` re-signs with a later expiry, same fingerprint. WKD serves the newest usable key then any revoked ones (migration 00070); an expired, retired or revoked own key is not advertised over Autocrypt | Accepted |
| [ADR-041](ADR-041-contacts.md) | Saved contacts (`saved_at`: set by sending to them, by isSaved, by VIP; never by a block; un-saving deletes nothing), the user's own name (`user_display_name`, never written by ingest) and capped notes, all synced; the mail counts and first/last mail dates are statistics that ADR-014 still exempts from change rows (the page sorts server-side). Merge keeps `from` as a hidden TOMBSTONE and records each moved address's and key's home, so separate can restore the other person into a NEW contact; a block wins (earlier stamp, stricter destination), keys follow the contact, pins stay per address, a shared key is combined. `contact-dates-backfill` is report-first, `--apply` opt-in, one change row per changed contact | Accepted |
| [ADR-042](ADR-042-agent-access.md) | Agent access. API keys are `mr_` + 256 bits of base32, stored as SHA-256 and shown once; `Authorization: Bearer` on the API routes only, every refusal one uniform 401, cookie+bearer refused, failures limited per address. One scope table gives every JMAP method a line and refuses any method without one (a walking test enforces it); Email/set needs every scope its contents need; a key's destroy is always soft. Account restriction inside the query/get/set paths; label restriction refused. Per-key rate and 24-hour budget at admission under the key's lock; mass delete refused and suspends, mass send refused, off-hours recorded, all pushed. Confirm mode holds send/delete as PendingActions that a person approves (re-validated, run through the same gate) or that expire after 24 hours | Accepted |
| [ADR-043](ADR-043-priority-promotion-gate.md) | The priority model is activated only through a gate against the cold start: at least 100 positives over 10 sender domains, sender-grouped 5-fold CV, recall at the 0.6 line better than the cold start by a paired Wilson bound (> 0.5 of the engaged messages they disagree on), precision within 0.05; otherwise the cold start serves and an active trained model is reverted, logged to audit_log. One balanced example per message, features as of arrival, no sender-identity features. Signals: Triage/open after a 4 s reading-pane dwell (session-only), replies from any client derived at ingest once per original, mark_read_no_open retired. priority-report / priority-reply-backfill / priority-train / priority-rescore are report-first | Accepted |
| [ADR-044](ADR-044-mcp-tools.md) | MCP tools. The standard Streamable HTTP transport at `/mcp`, stateless (no session id; GET/DELETE 405) with JSON responses; API keys only (a browser session 403, no credential 401 with `WWW-Authenticate: Bearer`). Every tool call is one JMAP request through the dispatcher and the ADR-042 key gate, nothing re-implemented; a method or set error is a tool error, a hold is a `pending_approval` result. A tool is listed only when the key's policy allows every JMAP method it declares (advisory; the dispatcher still refuses). Third-party text only under `untrusted_content`, every returned string stripped of control, bidi and zero-width characters. The official Go SDK v1.8.0 (Apache-2.0/MIT) behind `internal/mcp`, the only importer; tool names are a public contract; `move_to_mailbox`, not `move_to_area`, since areas are not open to keys | Accepted |
| [ADR-045](ADR-045-key-drafts-and-markdown.md) | An API key's own drafts. The draft tools' descriptions and results follow the key's send mode: without `mail:send` they say the owner sends the draft and never name `send_draft`; a hidden tool called anyway is still refused and audited by the dispatcher, and its error names the missing permission. A key's create identical to a draft it saved in the last 10 minutes (still a live draft) returns that draft, `alreadySaved`; matched on a KEYED fingerprint (HMAC under a DEK-derived key) in `app.api_key_drafts`, under a per-key advisory lock. `draft_update` (`replacesEmailId`) and `draft_discard` (`discardDrafts`) under `mail:draft`, only for the key's own unsent drafts with no pending send; the old version goes to Trash (spec §13a: no agent hard delete), and a key sends only drafts still in Drafts. Markdown bodies rendered by goldmark v1.8.6 (raw HTML escaped, links http/https/mailto only, images as alt text, hard wraps), sent as multipart/alternative with the body exactly as text/plain | Accepted |
| [ADR-046](ADR-046-mail-provider-oauth.md) | Mail-provider OAuth (Gmail, Outlook/Microsoft 365) with operator-owned clients: a registry fixes every provider host; the refresh token is sealed in `accounts.credentials_ct`, the queryable grant (provider, subject, scopes, state, rotation generation) is `app.oauth_grants`, access tokens live only in memory; connect is code + PKCE with single-use, user-bound `app.oauth_flows` rows and per-provider callbacks. Refresh is singleflight per account plus compare-and-swap on the generation; `invalid_grant` → needs_reauth (only the user can fix it), `invalid_client`/`unauthorized_client` → operator_error (users are not told to reconnect), the rest transient. A state transition appends an Account change row and an audit row; rotation appends none. XOAUTH2 behind `sync.Config.Auth` and `provider.SMTPAuth`, empty answer to the failure challenge, SMTP refuses cleartext; tokens redacted everywhere | Accepted |
| [ADR-047](ADR-047-gmail-all-mail-and-labels.md) | Live Gmail OAuth accounts sync All Mail, Spam and Trash once and map X-GM-LABELS to Mailroom labels, deviating from spec §4's label-folder example (which still holds for imports); writeback is `STORE ±X-GM-LABELS` with no EXPUNGE outside Trash and Spam; go-imap gets a small fork pinned with `replace` (offered upstream) because beta.8 cannot parse X-GM-*; full history newest-first under a 2,000 MB/day budget with an ETA and Stop | Accepted |
| [ADR-048](ADR-048-server-side-sessions-and-silent-renewal.md) | Browser sessions become server-side rows (`app.sessions`): the cookie holds a random secret stored as SHA-256, looked up through one SECURITY DEFINER function that also refuses disabled users; a store error is 503, never 401. The provider refresh token is sealed per user and renewed server-to-server at most every 15 minutes of use, serialised by singleflight plus a per-session advisory lock (single-use refresh tokens), 5 s bound; each renewal re-verifies the ID token's `sub` and re-runs the login resolver, so role and email changes apply within 15 minutes; a provider refusal revokes, an outage serves at most 12 hours past the last check; the 30-day idle limit is the provider's refresh validity. `SignedInDevice/get` and `/set destroy` (per device and *others*, not for API keys) revoke the row and the refresh token, delete that session's push subscriptions (the client re-registers on connect) and close its streams within a minute. Legacy cookies refused, so everyone signs in once | Accepted |
